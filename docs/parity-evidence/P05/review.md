## Initial findings

1. **Opening a terminal blocks the interface on full-package hashing and process startup.** `src/ui/packages.rs:30` enters `Workspace::start` from the button's render callback. At `src/ui.rs:976`, it resolves the launch synchronously. `src/packages/mod.rs:321` opens and hashes every installed executable, then `src/ui.rs:979` starts the PTY on the same thread. The 24 command names each contain a full BusyBox binary. Opening a tab from cold storage can stall other tabs, and a user cannot cancel the launch. The expanded tools panel also reopens and parses the registry on every repaint at `src/ui/packages.rs:49`. Move resolution and PTY creation to a pending-launch worker, deliver the lease with the process, and cache the displayed package state. Exercise the button and closing a pending tab with a deliberately delayed resolver.

2. **Cleanup can discard an unverified replacement and trusts mutable ownership metadata.** At `src/packages/mod.rs:543`, cleanup uses the editable inventory as its entire ownership authority. The pathname grammar at line 545 accepts additional filenames beyond the pinned release's list. At lines 552–555 it hashes an open file and then unlinks the current occupant of the name. The registry lock coordinates app instances, while an editor saving a replacement between those operations can lose the replacement. At lines 365–366, cleanup also unconditionally unlinks the lease and inventory by name. Validate receipt entries against authoritative release metadata and use a retirement procedure that preserves ambiguous replacements. Cover concurrent editor saves as well as ordinary preexisting edits.

3. **A nonregular package file can indefinitely stall open, removal, or cleanup.** `src/packages/mod.rs:476` uses an ordinary blocking open before checking file type. A FIFO at an expected package path on Unix can wait indefinitely before line 477 executes. Cleanup performs this I/O while holding the registry lock at line 346. Line 516 uses a fresh permanently false cancellation flag, and `cleanup()` checks cancellation only once at line 200. A blocked operation can outlive its UI and prevent subsequent package commands. Use nonblocking no-follow opens for regular-file checks, propagate the job cancellation through collection, and keep long cleanup I/O outside the registry lock. Verify prompt completion or cancellation for special entries and multiple retained versions.

## Evidence and limits

- Independently reran the private build's targeted binaries against staged upstream fixtures. The three Linux workflow tests passed in 7.05 seconds and both archive/architecture tests passed. The three staged archive SHA-256 values matched the recorded pins. The update test (`tests/package_manager.rs:42`) keeps an old **piped shell** alive while switching releases. The separate real PTY test exercises HOME and PATH. No test combines a live old PTY and an upgrade or launches a second app process to contend for locks.
- The installer authenticates the release, hashes a private compressed copy, and extracts from that same file. Raw tar iteration filters entry type and declared path, checks copy lengths, enforces size ceilings, assigns executable modes itself and verifies command bytes and architecture. The parser never explicitly checks the USTAR magic. Raw extended headers are rejected by the type filter. The unit test explicitly exercises a global extension header, and omits GNU long-name and short-body cases. The archive hash pins the exact accepted release bytes.
- A same-directory persisted registry file switches the active version. Unique staged directories and shared/exclusive file leases cover normal app-managed lifecycle. An existing tab owns its process and lease separately, in drop order. Public standalone launch callers must keep the Launch alive themselves. Crash recovery for abandoned staging directories and power-loss durability were not demonstrated.
- The Windows override path builds a UTF-16 child environment block; native launches with no overrides retain inherited process environment. Linux tests verify parent HOME and PATH. Windows native installation, locking, drive handling and ConPTY execution remain unverified. The staged source and license evidence supports the named BusyBox candidates. It does not establish Bash, Cygwin or complete Unix compatibility.
- Original-format evidence is limited to the inspected CygUtils.plugin ZIP and sampled LZMA members. MobApt, .mxt3 and original loader compatibility remain open. Full suite and merge validation belong to the integrated tree.
