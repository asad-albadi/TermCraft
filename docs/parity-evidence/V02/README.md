# V02 forwarding matrix implementation checkpoint

`tests/tunnel_interop.rs` exercises the actual production `model::Tunnel::args` → `process::Process::spawn` OpenSSH path used by `ui/pages.rs::tunnels_page`. Production uses an external OpenSSH PTY process; there is no separate embedded Tunnel or GatewayLease implementation to substitute into this suite. Closing the owned Process exercises the same lifetime primitive as tab/app cancellation; this suite does not claim rendered GUI action coverage.

The private fixture prepends `-F /dev/null`, batch authentication, strict host checking and its own known-host files. These isolate user configuration and never disable host-key checking. The OpenSSH endpoint binds only IPv4 loopback; forwarding listeners and echo destinations cover IPv4 and IPv6 loopback. Explicit alternate binds are 127.0.0.2 and ::1. The Linux run additionally inspects actual test-owned listening socket entries and rejects wildcard exposure. There is no LAN listener or host network change. Remote alternate bind uses the test-owned daemon's `GatewayPorts clientspecified` setting.

Every mode must carry exactly nine `TUNNEL_OK` bytes and reach one actual echo endpoint whose peer/local address is logged. Dynamic cases negotiate SOCKS5 no-auth and send IPv4/IPv6 CONNECT requests. Cases also observe forwarding diagnostics and process exit on bind conflict, failure on unavailable destination (actual channel close or explicit SOCKS refusal; a read timeout cannot pass), cancellation with a live channel, listener rebind, and two fresh process connections using the same saved Tunnel config. Fixtures own their sockets, keys, roots and child processes.
