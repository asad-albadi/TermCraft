## Source and security assessment

- The only new native changes relative to the prior keyboard/session-ready prepared source are in `os/xdmcp.c`, `os/connection.c`, and `os/osdep.h`. Existing keyboard and readiness hunks are retained. The only `XdmcpOpenDisplay` call site remains inside `ClientAuthorized`, after its existing authorization/host-policy rejection paths, assignment of auth_id, and connection timeout clearing. The guard does not alter authorization, the subsequent Xace hook, client setup/accounting, window ownership, or kill semantics.
- The explicit option is parsed once before the generation loop. It requires preceding readiness and rejects duplication. The Linux parent pidfd is retained for process lifetime, is CLOEXEC, and is not reopened during server resets. Failure to open it or a changed parent during setup is fatal. Platforms without this Linux support reject the explicit option; packaged support remains Linux x86_64 GNU, not a portability claim.
- Classification requires current parent PID equality, a retained pidfd whose zero-time poll returns no event/error, and successful native local transport credentials with both PID and UID fields matching the captured launching identity. The actual existing `GetLocalClientCreds` checks `_XSERVTransIsLocal` and uses kernel SO_PEERCRED on this build. Its successful allocation is freed; its failure paths free their allocations themselves. Any unknown identity, missing fields, poll failure, dead pidfd, UID mismatch, PID mismatch, or remote transport leaves the client eligible for ordinary native selection.
- PID reuse does not allow an unrelated process to become the live launching-parent class: the pidfd refers to the original process, and current getppid equality additionally excludes reparenting. The small liveness-check/credential-read interval does not create a new socket from a recycled PID before a successful live-parent check: a preexisting connected socket's kernel credentials identify its original peer. There is no credential supplied by the X11 client or cookie-derived role claim here. UID capture is valid for the reviewed unchanged unprivileged Rust launch path; a future launch with credential switching would require separate analysis.
- The class intentionally means authenticated sockets from the exact owning application process, rather than one cookie or a socket-family-wide class. A separately running legitimate manager, including same-UID AF_UNIX, cannot match the parent PID and remains selected normally. Existing ordinary last-client behavior and the existing sessionSocket close/reset path are unchanged, including -once semantics. The app-side sibling/wrong-cookie/real-manager operational controls remain complementary to the native fixture.
- Caller review confirms `session_ready` is true for bidirectional clipboard or explicit keyboard; only bidirectional clipboard appends the new flag, immediately after readiness. Keyboard-only sessions do not enable native exclusion. The existing stock selection branch is untouched. No auth scheme or caller cookie handling change is introduced by this flag.
