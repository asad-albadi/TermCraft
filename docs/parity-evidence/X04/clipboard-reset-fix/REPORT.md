## Cause and correction

Two linked problems are distinct. The existing run catches nested tick EOF, but a second reset during `Endpoint::new` escapes via `?`, including the final GetSelectionOwner reply. The private regression drives actual `run` and `Endpoint` against local X11 request streams, closes the first recovery at that final request, and requires another complete endpoint to initialize. Baseline RED is preserved in `evidence/red.log`. An additional existing-owner conversion EOF was separately RED: `begin(owner)` erased the transport kind (`evidence/owner-conversion-red.log`).

The native feedback cause and correction are owned by sibling packet `../xdmcp-c-lifecycle-diagnosis`. The pinned Xorg post-authorization path records the first authorized client during AWAIT_MANAGE_RESPONSE as its lifecycle client. Existing real traces correlate the bridge's setup resource base/window 0x200000 with xdm SecureDisplay/pseudoReset XKillClient 0x200000. Recording the internal bridge as the session client makes its normal manager-directed close initiate a new server reset. Native controlled original RED and fixed GREEN include real separate-PID Unix manager clients. C changes exclude only the explicitly opted-in authenticated exact live launching parent PID+UID from lifecycle selection; normal authorization, family guards, other clients, and nClients remain enabled. The caller passes the new flag only for Bidirectional clipboard, after the existing readiness flag. Keyboard-only and stock host-keyboard/Disabled behavior remain separate.

Rust recovery now retries the complete authenticated Endpoint only after typed UnexpectedEof, ConnectionReset, BrokenPipe or ConnectionAborted. Each attempt checks the same retained owned pidfd, freshly verifies SO_PEERCRED before cookie transmission, then authenticates/initializes within the original recovery deadline. Cancellation, expiry, authentication rejection, protocol errors and identity mismatch remain fatal to that recovery. Partial endpoints are dropped, and no extra budget is allocated. The existing three-recovery-episodes/30s protection is unchanged; initializer attempts inside one episode share its original two-second budget. Parent clearing precedes recovery and current selection resampling follows successful recovery, preserving external parent ownership and avoiding old nested-history replay.
