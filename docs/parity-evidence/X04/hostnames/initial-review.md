## Findings

1. **Blocking spec and quality — editor lifetime is actually profile lifetime.** Candidate src/ui/xdmcp.rs:26–47 resets State only if the session ID changes, and :62–81 advances the request generation only when the input fingerprint changes. Existing integration src/ui/pages.rs:113–116, :172 and :268–275 does not clear XDMCP state when the dialog closes by Cancel, window close, Save or Connect, or when leaving the XDMCP protocol. Reopening the same profile with the same host/port/mode can show stale candidates or recognize a saved endpoint as an editor-bound choice from the previous lifetime. If a user clicks Discover and closes immediately, reopening the same profile before the DNS deadline can consume the former dialog’s completion and initiate UDP discovery inside the newly opened dialog's render at candidate src/ui/xdmcp.rs:82–100. An earlier explicit click is not authorization to resume discovery in a different editor generation. Reset/drop state at the real dialog and protocol lifetime boundaries, while keeping it during retained validation-error frames. Add a same-profile reopen test showing no reused binding, no reused candidates and no late DNS-to-UDP transition. Maintain the nonjoining Drop path.
2. **Important quality — stale results stay selectable during or after a new resolution.** Candidate src/ui/xdmcp.rs:158–168 and :196–209 do not clear prior resolved candidates, and :196–209 also leaves prior discovered endpoints. Both lists remain interactive at :221–257, including after the new resolver returns an error at :103. A changed DNS answer or error can therefore leave a stale row labelled “Use resolved IPv4 endpoint,” which becomes a preference and then fails fresh Connect. Separate current in-flight results from old rows. Hide/invalidate old lists when a new explicit request begins, and keep any deliberate existing Discover preference separate until fresh membership is checked. Prevent old rows from being re-bound to a new generation. Add a successive request failure or answer-change test. Do not bypass or weaken the fresh Connect check.
3. **Evidence integrity — exact candidate and latest verification are different inputs.** The patch, payload and sealed source agree on src/x11/xdmcp_host.rs SHA-256 2720480962fda4ca3d7ac51c9ed9577cee7137ca6459afe835942718bcccae41. Mutable private source is 21a8bb9a97dad5a9e5cd87636161563b1f24ca13226120e3741607496b5056be due to an added test-only AAAA/mixed test at mutable :396–424. The latest focused logs record 27 passed/2 ignored and UI 5 passed, and the normal build log names mutable private source. Do not claim all those logs verify the sealed snapshot. Reseal source and patch maps, binary and tests, including focused and live logs tied to the exact corrected candidate. The live verification script currently hard-codes a hashed Cargo test binary path (verify.sh:13), which risks running a stale executable after rebuilding, introducing a new identity, or repeating from another checkout. Derive the path from Cargo's executable artifact for that build.
4. **Scope/evidence distinction — the 32-address limit is application admission, not a bound on std/OS materialization.** Candidate src/x11/xdmcp_host.rs:73–77 calls ToSocketAddrs before take(33), and :161–176 caps application admissions and deduplication. Local Rust 1.99 standard-library source docs, src/std/net/socket_addr.rs:200–213, show the tuple implementation eagerly calls Vec::from_iter(addrs). The candidate's own result vector is bounded, but the preceding std allocation and OS answer are not. Report that distinction accurately. If the requirement is instead to bound userspace conversion, the backend would need bounded iteration starting at the native answer list. Preserve the two-call permit until actual OS return under either approach.
