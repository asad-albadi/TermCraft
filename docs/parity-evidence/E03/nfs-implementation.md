This delivers the confirmed NFS service slice, not E03 completion. ## Export and security contract

- Embedded, application-owned NFSv3 + MOUNTv3 on **one configurable TCP endpoint**, export `/share`. Default UI endpoint `127.0.0.1:20490`, read-only, 360-second adjustable lifetime. The UI and configuration require an explicitly selected absolute folder; non-loopback binding requires explicit opt-in. Occupied ports fail clearly.
- No UDP NFS, NFSv2/v4, TLS, password authentication, system portmapper, mount command, privileged helper, daemon/config changes or user impersonation. No system NFS client mount is performed in validation.
- AUTH_SYS and AUTH_NONE are accepted; supplied UID/GID credentials do **not** confer OS identity or authentication. All clients act with the application's current account and selected export permissions. Reported UID/GID are synthetic zero, not a claim of root execution. No permission-elevation calls exist. This is a trusted-peer sharing mode; the UI states its lack of password/encryption.
- Read-only is checked by every implemented mutation, with `ReadOnly` defaults for unsupported mutations. Explicit full-write opt-in permits existing-file updates/truncation, creation, deletion, directory creation/removal and ordinary rename destination replacement. Normal filesystem replacement may replace concurrent external destination edits; there is **no** target compare-and-swap promise. NFS writes are per-request operations, not whole-upload atomic transactions; committed earlier chunks remain after disconnect/stop.
- CREATE supports GUARDED (`create_new`), UNCHECKED (pinned existing descriptor, optional size), and server-lifetime EXCLUSIVE verifier retry. New files are created with restrictive current-account permissions (0600 on Unix); client mode requests do not expand permissions. SETATTR supports file size, not chmod/chown/times or guarded updates. Hard links, symbolic links, devices, FIFO/socket creation and READLINK are unsupported. These are explicit limitations, not original-format parity claims. No persistent lock manager, ACL or filesystem-wide POSIX permission emulation is provided.

## Confinement, ownership and bounds

The backend reuses `files::Share`'s cap-std root and no-follow traversal. It stores opened files/directories, monotonic object IDs and a random per-export generation; subsequent access compares current no-follow path identity against the pinned descriptor. Replaced/deleted names and foreign export keys become stale. Unix names retain raw bytes; Windows accepts valid UTF-8 component names and rejects reserved/device/alternate-stream syntax. Dot/dotdot, slash, backslash, colon, NUL and control-name attacks are rejected. Rename keeps opened source/destination directories and a source descriptor; it never follows a final symlink. These are capability and path-identity protections, not a filesystem transaction against arbitrary concurrent external renames.

Each export has two runtime workers; at most eight connections, two requests per connection and eight total inflight requests; 128 KiB RPC records/fragments, four fragments, 64 KiB read/write/readdir replies; 1 MiB request buffering, reply buffering and replay cache; 128 replay entries and 16 mount entries. The filesystem table/directory enumeration is capped at 4,096 entries, path depth at 64, creation attempts at 256, individual mutation file size at 64 MiB, cumulative incoming writes and conservative growth reservations at 64 MiB each. Charges precede writes/creation so partial I/O errors cannot bypass quotas. Directory cookies include the sorted byte-name fingerprint and mutation epoch, and skipped inaccessible/symlink entries cannot create a non-progressing empty page.

Request deadline is five seconds, idle input deadline ten seconds, service cancellation polled every 50 ms, shutdown drain timeout one second. `nfsembed` tracks connections and RPC executions with JoinSets, aborts and drains them at shutdown. **`ServerHandle::shutdown()` only signals; the wrapper explicitly awaits `wait()` before its runtime returns.** No detached per-client task or subprocess is launched. Stop closes only owned listeners/connections. Bounded synchronous capability-filesystem calls run outside the UI thread; their underlying OS/storage I/O cannot be forcibly interrupted by a Rust future timeout. Slow/unresponsive filesystems can therefore delay shutdown beyond the measured local-filesystem result. Native Windows/macOS runtime and adverse-storage validation remain open.

## Hard-link confinement correction after independent review

The review reproduced WRITE and truncate changing an outside-named alias of a regular file exported through an existing hard link. Mutable regular-file opens now require exactly one link according to metadata from the held descriptor; WRITE, size SETATTR and UNCHECKED CREATE recheck that held descriptor immediately before content mutation. Previously cached handles also lose write ACCESS when an extra link appears. This conservative policy fails closed for multiple-link regular files in writable exports. Read-only exports may read an explicitly selected alias. Directory entry rename/removal retain ordinary namespace semantics, without changing the aliased inode contents.

This is an observed-link policy, **not** a kernel-atomic link-count comparison/mutation. A malicious same-account local process can still create another link between the final check and the filesystem operation; no prevention of arbitrary simultaneous same-user linking is claimed. Ordinary single-link file updates, truncation and authorized destination replacement remain supported.

`nfs-hardlink-red.log` records two failing tests before the fix: direct backend WRITE/SETATTR/UNCHECKED CREATE all succeeded, and an independent libnfs client reported all three unauthorized successes. `nfs-hardlink-green.log` records the same two tests passing after the fix. The final nine-component/ten-app-library regression includes those tests and the original seven/eight tests. The independent client obtains a write handle while the file has one link, creates an outside alias using owned fixture paths, proves WRITE and ftruncate fail on that cached handle, proves a fresh mutable open and create/truncate fail, and confirms outside bytes remain `original`. It then reads the same alias through a separate read-only export. Native source checks and the existing Servers pointer test are rerun against the corrected source. No broad suite or MAIN source edit was performed by this worker.
