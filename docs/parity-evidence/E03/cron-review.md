# E03 managed Cron independent review

2026-11-24. Reviewed the private candidate under `target/agent-work/e03-cron`, its normalized `cron-private.patch`, all 11 candidate hashes in `cron-base-hashes.json` (matched), implementation notes, and existing targeted verification logs. No production files were changed and no builds or broad suites were started during this review.

**Result: changes requested for the two issues below.** This is a review of the managed Cron slice, not completion of E03 or original-runtime equivalence.

## Findings

1. **[P2] Sync the schedule directory before claiming a durable attempt.** `target/agent-work/e03-cron/src/services/cron.rs:303–310` syncs the staged file contents and renames it into place, but never syncs the containing directory. `cron.rs:480–489` then starts the command on the premise that its attempt watermark is durable. After a machine/power/filesystem crash, the replacement directory entry can be lost even though the staged file was synced; the older watermark may reappear and a restart in the same due minute can repeat command effects. This undermines the documented durable at-most-one-recorded-attempt guarantee. Finish the platform-appropriate directory/replacement durability barrier before allowing command launch, and propagate failures. Ordinary application-process termination is a narrower guarantee that the existing implementation does provide.

2. **[P2] Preserve the edited job selection after saving.** `target/agent-work/e03-cron/src/ui/managed_cron.rs:158–163` clears `selected` after every successful save/reload, while retaining all populated form fields. The save handler at `managed_cron.rs:246–248` then treats the next edit as a new job. Concrete sequence: select an existing job, change its schedule, save successfully, change its schedule or enabled checkbox again, and save; the second save appends the same ID and fails unique-name validation instead of updating the job. Newly created jobs have the same issue immediately after their first save. Preserve/reselect the saved job by stable identity; when reload/removal invalidates selection, clear or explicitly reset the editor. Extend the pointer fixture through two consecutive edits of the same job without clicking its selector again.

## Scope and evidence assessment

- Existing logs support 11 service tests and 6 managed UI tests passing. Real Linux commands cover once-per-minute/restart watermark behavior, disabled jobs, forward-jump skip, rollback suppression, exclusive same-store ownership/live-save refusal, descendant cancellation with an unrelated process alive, runtime/service deadlines, concurrency limit, and nonzero result/output privacy. Calendar fixtures cover day-field rules, leap/impossible dates, names, actual child-process local timezone DST gap and repeated instants. The pointer fixture saves, starts a real supervisor/command, observes Running and command effects, stops, and persists a disabled job. It does not cover consecutive edits (finding 2) or machine-crash durability (finding 1).
- The candidate reuses the existing `Process.exit_message` API; there is no new process-backend delta in the authoritative patch/hash manifest. Actual Unix source retains the unreaped session leader while signalling foreground/leader groups, joins its bounded output reader, then kills/waits the child. Windows source launches suspended, assigns a kill-on-close Job Object before resuming, and closes that ownership on drop. Cron discards bounded output, copies only the backend numeric status message, and drops processes on timeout, stop, return, and owner teardown. The exit-17 fixture proves numeric reporting without command/output leakage on Linux. Unix signal termination uses the pre-existing generic status string, and native Windows/macOS execution is unverified.
- The Windows/macOS component checks import actual Cron, process and private-file implementations, with only the supervisor Context facade substituted. They establish compilation of those components, not native execution or whole-supervisor integration. The whole Windows attempt is explicitly blocked by missing `lib.exe`, not a pass. Existing format evidence is targeted to changed Rust files.
- Scheduler/save exclusion uses a separate private lock file held for the worker lifetime, including while replacing the configuration inode. Active edits are refused in both the worker and storage API. Configuration is bounded/versioned, validates explicit absolute local executable/folder paths, and has no added CLI/URI/remote job-import path. Final files/locks are verified private regular current-account single-link files; the reused helper rejects final-component symlinks/reparse points. Ancestor-directory symlinks are not rejected by this implementation; no stronger root-confinement claim is established here.
- Scheduling, disk work, and process lifetime work run off the UI thread; actions/snapshots and process output are bounded. Static supervisor logs omit command arguments and output. The manifest patch preserves existing root X05 Session fields and P06 password wrapper/UI modules; integration must still preserve any parent changes made after the recorded base.

## Non-blocking observation

`cron.rs:459–460` computes next-run from the current wall clock without considering the persisted high-water mark. During a clock rollback, the displayed next-run can therefore name an instant that `cron.rs:465` will suppress. A more accurate status would search beyond the high-water mark (while retaining the documented no-replay policy). Scheduling itself follows the stated rollback policy.
