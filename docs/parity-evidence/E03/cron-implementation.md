## Behavior

- Supervisor-owned Cron worker, identified by `ServiceId`, supports asynchronous start, cancellation, stopped/failed status, bounded metadata logs, and optional 1-second–24-hour service lifetime. The UI leaves the scheduler active until explicitly stopped or the workspace closes. No OS crontab, daemon, elevated account, or background-at-login installation is used. Scheduling is inactive after service stop or application exit.
- The Servers card supports creating/selecting/editing/removing named jobs, an enabled checkbox, saving/reloading, selectable UTC/system-local timezone, explicit executable/arguments/working folder, maximum process runtime, start/stop, next-run UTC timestamp, last event and numeric exit result. Start must be requested explicitly; saved enabled jobs do not start a scheduler automatically. Editing requires stopping the service.
- Configuration and durable attempt watermarks live in `services/cron-jobs.json` beside workspace settings, separate from credential/session JSON. Read and write use private regular single-link files owned by the current account; Unix mode is 0600 and the Windows candidate uses the existing private-file ACL implementation. Atomic staged replacement and versioned bounded decoding reject malformed/oversized/unknown-field configuration. Invalid saves preserve the existing file. A corrupt file is rejected, preserving the UI's last successfully loaded jobs; automatic recovery from an externally corrupted file is not claimed.
- A private lock file gives one scheduler/save exclusive ownership of a schedule store, including across app instances. Save refuses active-store mutation. Each job's due minute is persisted before launch. The staged contents are synced, then the replacement and its containing directory are committed before launch (platform details below); a failed commit stops scheduling without executing that due command. Ordinary execution runs once for a due minute, including restart within that minute. Crash semantics are **at most one recorded attempt**, not transactional exactly-once process effects: a crash after persistence but before spawn may omit a run.
- Only user-authored local jobs are supported. An existing absolute executable and absolute working folder are mandatory; scripts require their explicitly selected interpreter and arguments. No URL, inbound protocol, shell interpolation, or remote-file-to-command launch path was introduced. Jobs inherit the current account/environment and have its full authority. Credentials are not modeled; users are told to keep tokens/passwords out of command arguments and use their command's secure credential store.
- At most 32 jobs, 4 concurrently running processes, no overlapping run of one job, 64 arguments per job (8192 bytes each), 256 KiB configuration, and 1–86400-second process runtime. Overlapping/resource-limited due runs are skipped with a visible event, not queued for catch-up. Next-run search is bounded to 8 years. Logs use the existing 32-entry supervisor bound and contain static lifecycle metadata only. Process output is discarded, never displayed or logged; the reused production process backend has bounded queues (256 × 32 KiB output chunks per process), drained by the scheduler.
- Disk, calendar, command and cancellation work happens on owned background workers. UI actions use a bounded queue and snapshot. Dropping the controller closes its action channel; its background owner drops the supervisor, cancels its workers and owned processes. Unix uses the existing unreaped leader/process-group cleanup; the Windows candidate uses the existing suspended launch followed by kill-on-close Job Object ownership. Unrelated processes are not targeted.

## Supported calendar syntax and time policy

Exactly five whitespace-separated fields: minute (0–59), hour (0–23), day of month (1–31), month (1–12 or JAN–DEC), weekday (0–7 or SUN–SAT; 0 and 7 mean Sunday). Names are case-insensitive. Supports `*`, comma lists, inclusive ascending ranges, and positive steps on wildcards/ranges/single starting values (single value with step extends to field end). When neither day field starts with `*`, day-of-month and weekday use OR; otherwise both field selections must match. Rejects aliases (`@hourly` etc.), seconds/year fields, wraparound ranges, `?`, `L`, `W`, `#`, environment assignments and unsupported tokens.

UTC has no DST transitions. System-local uses the system timezone through chrono's production Local backend. A nonexistent local minute is skipped; an ambiguous repeated local minute has two distinct UTC instants and can execute twice, once for each instant. Next-run enumeration considers both. Missed minutes during pause, forward clock jumps or downtime are skipped: the current observed minute alone is eligible. A persisted per-job UTC-minute high-water mark suppresses repeated attempts during clock rollback and same-minute restart; it also means schedules do not replay recorded instants while a clock is behind that mark. No guarantee for commands that deliberately detach themselves into new sessions/jobs is claimed.

## Independent review follow-up (2026-11-24)

The two P2 findings in `cron-review.md` and its next-run display observation are addressed in this refreshed private candidate; scoped independent re-review is pending.

1. **Commit durability.** `persist_with_barrier` syncs actual staged file data, performs replacement, then completes the platform commit boundary before the scheduler can spawn commands. Unix opens and syncs the parent directory; macOS additionally opens the resulting file for writing and requests `F_FULLFSYNC` after the directory sync, returning an error if unsupported or unsuccessful. Windows replaces the same-directory stage using `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`, without cross-volume-copy or delayed-reboot flags; embedded NUL paths are rejected before the raw API. The Windows barrier is the write-through replacement itself, whose result is checked. [Microsoft documents MoveFileExW write-through completion](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw). Storage must honor the requested OS flush semantics; actual power-cut recovery and native Windows/macOS durability are not claimed as tested.

   `cron-durability-red.log` records the missing commit-boundary API before implementation. The new real-filesystem fixture pauses the private commit boundary **after an actual staged/synced file has replaced the watermark file**, reads that real watermark, proves no marker-producing command has run, injects a directory-commit failure and observes Failed with no execution, then advances to the next minute and releases through the real native barrier to observe exactly one actual process effect. This proves production commit/launch ordering and failure handling on Linux; it does not simulate a physical power cut. The boundary is private to the Cron module, with the native implementation selected by the public config constructor.

2. **Consecutive saves.** The background save acknowledgement carries the successfully saved job identity. A refreshed snapshot selects that identity and repopulates the editor; explicit reload preserves a still-valid selected identity, and removal or invalid selection resets the editor. New-job selection is therefore retained after its first save. The extended production-card pointer fixture reproduced the duplicate-ID failure before the fix (`cron-edit-red.log`), then passed after two consecutive schedule edits and saves without choosing the job again. The same fixture still starts a real command, verifies status/effects, stops it, changes enabled via pointer, and recreates a controller to verify one persisted disabled job with its edited schedule.

3. **Rollback display.** Next-run status now searches after the later of the observed clock and the persisted attempt minute's end. The real command/rollback fixture asserts that the next-run instant is beyond the suppression watermark, while execution remains suppressed during rollback.
