**PASS: 68 fresh verifier checks, zero failures**, in a configured private Linux native headless environment. `python target/agent-work/real-wayland-rd/verify.py` checks the real observations. ## Important headless fixture attribution

The initially device-free seat exposed a real initialization race: the first injected ordinary key-down created the compositor virtual keyboard; the receiver only then learned the keyboard seat capability and bound its keyboard, too late for that down. Its up and later down/up arrived. This was **reproduced independently through genuine direct Mutter calls with no production provider involved**: direct-native-comparison/direct-inputs.jsonl, owned-target.log, target/events.jsonl show initial `wl_seat.capabilities(0)`, then after first raw key request `capabilities(2)`, `get_keyboard`, `keymap`, `enter`, first key-up, repeated key-down/up. This is not hidden or “fixed” in product code.

The authoritative configured-platform matrix models an already-present desktop keyboard using a **separate fixture-owned virtual keyboard, established before target mapping and before any product provider exists**. A neutral Shift down/up to the owned compositor initializes it. reports/fixture-keyboard-primer.json and keyboard-ready-before-provider.json prove keyboard capability, binding, keymap and focus enter were complete before the first production event. The first actual production `a` down/up then both arrived on raw Wayland wire and GTK telemetry. No fake portal, provider priming workaround or source change was used. The result qualifies a private native desktop with an existing keyboard; it does **not** promise first injected-key delivery to a client on a completely keyboard-less seat that has not bound wl_keyboard yet.

Retained unprimed runs and direct comparison preserve this counterexample. A separate fixture race involved the owned target mapping late and stealing focus from consent; readiness now checks actual target pixels before opening permission dialogs. The private command-file harness also once observed a partially written request; it now publishes commands by atomic rename. Those are fixture-only changes; all production bytes remain exact.
