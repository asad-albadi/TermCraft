2026-11-25. Reviewed private `target/agent-work/vnc-macos` only; no implementation changes, host capture, permissions, input, clipboard access, GUI build, or broad Cargo build. Candidate integration patch SHA-256 `fcceca1bb4b7d20afea908a32b115dec1dd89ceb5f237a30cd7e6c24d58b5a9c`.

## Verdict

**Two Important findings; no Critical finding identified. Not approved for integration unchanged.** The accepted initial macOS14/5fps scope and one-line vendor-code patch do not excuse these input/lifetime defects. E03 stays open and strict parity stays unchanged.

1. **Important — middle-button dragging posts the wrong button** (`src/services/vnc/macos.rs:373–384`, private candidate). When the owned center button is down (`self.buttons & 2`), movement chooses `OtherMouseDragged` but passes `CGMouseButton::Left`. Down/up correctly use Center. Thus a center-button down/move/up sequence has an inconsistent drag button and can fail middle-button application interaction. Select the matching button together with the movement type and cover all three drag mappings with a pure planner check. Apple states that mouseButton is used for OtherMouseDragged (also OtherMouseDown/Up), whereas it is ignored for left/right event types. [Apple CGEventCreateMouseEvent](https://developer.apple.com/documentation/coregraphics/cgevent/init(mouseeventsource:mousetype:mousecursorposition:mousebutton:)).

2. **Important — secondary-thread Cocoa work has no autorelease pool** (`src/services/vnc/macos.rs`, especially open at 208 onward, screenshot callbacks at 72/119, clipboard at 449 onward). The VNC source runs on Rust-created worker threads; neither the candidate nor the existing VNC worker supplies an `objc2::rc::autoreleasepool`. These calls create/use Foundation/AppKit/ScreenCaptureKit objects repeatedly, including clipboard strings. Explicit Retained ownership covers owned references, not autoreleased framework temporaries. Cocoa secondary threads need their own pool and long-lived work needs periodic draining. Without bounded scopes this can accumulate objects over the session even though the Rust frame queue and capture permit are bounded. Add bounded pools around native work, including completion bodies where the provider should not depend on an undocumented callback queue pool; retain/copy all data that outlives each pool. Actual leak magnitude is unmeasured here. [Apple autorelease pool guidance](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/MemoryMgmt/Articles/mmAutoreleasePools.html).

## Integration dependency and accepted limitations

The dispatch hunk deliberately references `cancel.clone()` provided by the separate Wayland/supervisor interface. MAIN currently lacks that interface. Passing structural dry-run and component checks is **not** a claim that this patch alone compiles as the application. Merge must preserve existing X11/Windows dispatch and shared cancellation.

Accepted initial scope: macOS14+ single-frame SCScreenshotManager backend capped at 5fps, selected display only, global one-native-job cap, vendor maintenance cost. The image API supplies CGImage/error, not CMSampleBuffer status attachments; no attachment-status claim is made. [Apple capture-image API](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager/captureimage(contentfilter:configuration:completionhandler:)).

Still UNAVAILABLE: real macOS14/15/26 capture, permission prompt/revocation, input/clipboard roundtrip, monitor hotplug/Retina mapping on hardware, repeated Start/Stop with OS callbacks, memory/performance measurements, final Mach-O linking and actual older-supported-macOS ordinary application startup. macOS12/13 capture unsupported. The dynamic-load/source/LLVM work reduces the strong-link risk but cannot certify final Mach-O dependencies or old-OS startup. Native findings remain open; none of this closes E03.
