## Implemented clipboard behavior

Clipboard sharing remains disabled by default, with a separate Servers-card opt-in. It acts only on the explicitly selected display/source. A view-only listener may export selected-source text; it never applies remote clipboard writes. Keyboard/pointer consent remains separate. No clipboard strings are logged or included in Debug output. Clipboard contents are transient, bounded and zeroized in the server's retained buffers. No capture file or clipboard persistence file is created.

Linux uses actual X11 **CLIPBOARD selection ownership and conversion**, on the provider's already selected/authenticated connection. A private InputOnly window owns incoming remote text, serves UTF8_STRING and representable Latin-1 STRING targets, and advertises TARGETS. Outgoing source text is obtained with ConvertSelection and SelectionNotify/GetProperty, with UTF8_STRING preferred and STRING fallback. PRIMARY and CUT_BUFFER properties are never read or written. Same-owner clipboard edits are polled every 500ms and compared before publishing. Selection event processing is asynchronous and bounded to 64 events per source tick; a nonresponding selection owner times out after one second. The existing X11 transport's two-second operation deadline still bounds transport waits. Large INCR transfers, COMPOUND_TEXT, binary/image/file clipboard formats and clipboard-manager persistence are not supported. Unsupported types/oversized properties are never treated as text. Stop drops only this provider's connection/window; an owned selection disappears, while a different owner's selection remains intact.

The server now sends ServerCutText and accepts ClientCutText. Classic text is Latin-1, with no lossy Unicode replacement. Non-Latin-1 source text requires the viewer's extended clipboard negotiation. The server advertises the extended clipboard pseudo-encoding only in response to SetEncodings, exchanges capabilities without a capabilities reply loop, and supports bounded Notify/Request/Provide/Peek with compressed UTF-8. It follows the existing embedded client's validation and text normalization. Extended traffic before negotiation, invalid compressed payloads, oversized text, trailing compressed data, NUL-containing text and invalid UTF-8 are rejected or ignored according to the negotiated action/policy. A requested Provide is required before accepting extended text. Bounds are 8 KiB normalized UTF-8 text and 32 KiB received clipboard messages; the existing five-second body/write deadline and bounded input queue remain. Unicode source text is withheld from a classic-only viewer instead of silently replacing characters.

Only selected-source changes are published to viewers. A remote write clears the old published snapshot and takes selection ownership without republishing that remote text, preventing echo. Each client retains its own negotiation/revision state. Network polling checks cancellation and periodically sends source changes even when a viewer sends no framebuffer request. Existing input ownership and held-key release paths remain intact.

Windows has an actual **CF_UNICODETEXT component-checked candidate**. It creates a message-only window lazily on the source worker, checks the active input desktop before clipboard operations, opens the clipboard without an unbounded retry loop, bounds GlobalSize before reading, validates UTF-16, normalizes CRLF/LF, and transfers GMEM_MOVEABLE ownership only after SetClipboardData succeeds. Clipboard sequence numbers suppress polling duplicates and remote echo. It destroys only its own message-only window; eager data transferred to Windows remains owned by the OS. Additional Windows dependency features are DataExchange and Memory, on the existing locked windows-sys version. There is no new runtime binary/dependency on Linux and no shell/external clipboard utility.

**Windows is not runtime-qualified.** Native clipboard contention, delayed-rendering owners, permissions, cancellation, GDI capture, control and DPI behavior have not run on Windows. Synchronous GetClipboardData/other Win32 calls cannot be given a reliable Rust cancellation deadline, so a delayed-rendering clipboard owner remains a possible Stop-responsiveness limitation, alongside the prior GDI limitation. The Windows candidate is not represented as tested native support.

## Explicit remaining source/parity scope

The root coordinator split the remaining native sources into a fresh follow-up after this clipboard handoff. **Wayland ScreenCast/RemoteDesktop portal authorization with actual native PipeWire frames/control is not implemented or tested by this patch. Native macOS ScreenCaptureKit capture, input permission/control and clipboard are not implemented or tested.** Their current explicit unavailable responses remain; neither source falls back to capturing the host. A private D-Bus/portal protocol fixture alone would not constitute actual host portal qualification. Any future live testing must preserve the no-host-capture/no-host-input constraint and must not accept permission dialogs automatically.

Browser/HTTP viewer behavior, exact original TightVNC access/settings parity, Windows native qualification, secondary-monitor selection and the existing platform gaps remain outstanding. Clipboard completion does not close E03 or infer the browser/HTTP requirement away.
