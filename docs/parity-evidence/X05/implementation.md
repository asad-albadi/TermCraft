# X05 private implementation and evidence

Candidate source: `target/agent-work/x05/` (Cargo version `0.1.0-x05-private`). Production files have not been integrated by this worker. Parent performs fresh review and integration.

User-owned saved SSH sessions gain `RemoteEnvironment::{None,Preset,Custom}`. Legacy JSON defaults to None and omits the field when saving. Presets start `dbus-run-session -- xfce4-session`, `mate-session`, `startlxqt`, or `gnome-session`; these require the corresponding desktop and D-Bus tools on the remote host. GNOME specifically requires an X11-capable installation. Custom is an explicit remote `sh -lc` command, bounded to 8192 bytes, serialized as one quoted SSH argument. It is never executed on the client.

The session editor separates this choice from forwarding an ordinary X application and documents remote dependencies and display compatibility. The installed OpenSSH adapter explicitly rejects a selected environment instead of silently ignoring it. Embedded SSH resolves its configuration once as before; remote-environment launch consumes that resolved session and the existing per-connection X forwarding lease. Read-file and desktop-gateway purposes return before terminal startup. No new import/URI/file command surface is introduced: inbound links still accept bookmark identifiers or folders only, and reject environment fields.

After the shell starts, one additional SSH channel requests X11 and executes the chosen command. Its launch request is confirmed before Connected releases the startup macro queue. The worker does not wait for desktop exit. Output/status monitoring uses one owned JoinSet task and the existing bounded event queue. Startup/setup errors and nonzero exit status are reported in terminal output and session state; the shell remains available. Setup is bounded to ten seconds; rejected/timed-out setup closes its channel. Connection cancellation drops the task and its existing forwarding lease. No global DISPLAY/XAUTHORITY modification or terminal input injection occurs.

No live host display start/stop/socket operation was performed by this task.

The test SSH server executes actual `/bin/sh` processes and the selected command, and provides authenticated X TCP proxies that relay over real SSH X11 channels. A child test executable receives the forwarded display/cookie, maps an X window, and an independent owned-display connection verifies VIEWABLE. The selected command appends exactly one launch marker; the unrelated session has no environment channel and its real shell continues executing commands. Cancellation removes the first mapped window while the unrelated session's X forwarding and shell remain usable. Cancellation while awaiting an unconfirmed launch also leaves the other session functional. A missing binary exits 127, reports an error, and a subsequent command executes in the same real persistent shell. No-X-forwarding selection also reports an error while preserving that shell.

This is launch/lifecycle evidence using a mapped-window fixture, not proof of a full desktop session. Native Windows/macOS runs, installed XFCE/MATE/LXQt/GNOME full-desktop visual/interaction validation, remote display-manager compatibility, and original-product comparison remain explicit gaps. The fixture must never be described as full-desktop parity. No whole-suite result is claimed by this private worker; the parent owns the merged gate.

Rulings: dedicated SSH exec channel preserves shell input and macro ordering; one shared per-connection forwarding lease covers shell/desktop channels. Unsupported installed-engine configuration fails clearly. Preset availability is remote-host dependent and no packages are installed by startup.


## Important review finding fixed — startup output progress

The independent review found that russh's single packet dispatcher could block on the shell's 64-message channel receiver while the worker awaited a desktop-channel confirmation. Added `startup_output_does_not_block_desktop_confirmation_or_cancel`: the real SSH fixture queues 192 distinct shell output messages, each with a 1 KiB payload, after shell success and before desktop exec confirmation. RED (`flood-red.log`) observed no terminal bytes and Connected=false after four seconds. This reproduces the cross-channel stall before the old ten-second timeout.

The private worker now polls shell messages concurrently with the existing ten-second environment handshake. It sends them through the existing bounded event channel in at most 16 KiB chunks. No additional output task, queue, configuration resolution, or terminal input path was introduced. Connected still follows desktop exec confirmation; the ordinary terminal reader takes over afterward. Shell close/status during startup retains its existing terminal exit semantics. Cancellation still interrupts the whole worker independently of a full event queue.

GREEN: final focused tests 5 passed, 5 ignored (the ignored helper is not a product case); four actual private SSH/owned-X live cases passed, including all three previous cases and the new flood regression. The new case observes successful desktop output and Connected within four seconds, all 192 distinct startup frame markers exactly once, no reported environment error, output polling capped at 4096 bytes per call, and a subsequent real shell command. A second connection leaves output unconsumed so bounded queues back up; cancellation completes within two seconds while its launch cannot make progress. `unit-final.log`, `live-final.log`, and `fmt-final.log` are refreshed. Full desktop/native-platform gaps above remain unchanged. Parent owns scoped re-review and merged gating.
