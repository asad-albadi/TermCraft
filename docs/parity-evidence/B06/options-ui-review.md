## Important finding

**[P2] Keep focused option-editor keys out of the live board** — `src/ui/games/play.rs:720–721` in `target/agent-work/b06-options-ui`.

`games_frame` copies all input events and forwards every pressed key to `play.key` before drawing the options controls, without respecting the focused egui numeric editor. The new sliders expose editable numeric values, so the same input changes both a pending setting and the current board. An independently compiled actual-input regression opens a default Guess game, expands Puzzle options, allows the animation to settle, clicks the displayed colours value 6, verifies `ctx.egui_wants_keyboard_input()` is true, then sends Num3 plus Text("3"). The pending draft correctly becomes colours 3, but the current six-colour game's row also changes from `[0, 0, 0, 0]` to `[3, 0, 0, 0]`, without New game. This violates the promised pending-until-New-game behavior and creates an unintended move/history entry while editing settings. The same unconditional route also accepts Enter, arrows and undo/redo shortcuts while an options editor owns input.

Route gameplay shortcuts only when the options widgets do not own/consume the keyboard, while retaining foreground/root ownership and Close quarantine. Add a real numeric-control editing regression proving the draft changes while live scene, selection and undo/redo history do not; cover Enter finishing an edit and focused Ctrl+Z as well. This is a correction to the new options surface, not a request to expand advanced-game scope.

Evidence: `docs/parity-evidence/B06/options-ui-review-keyboard-probe.log`. The test deliberately fails the expected unchanged-scene assertion after confirming actual widget focus; its output independently shows both changed draft and unintended live peg.
