# X02 owned X display and SSH forwarding

The Local and SSH forms can explicitly select TermCraft or System. New profiles created from the session form select TermCraft on the packaged Linux platform. Profiles saved without a display selection keep the System behavior. X11 remains opt-in. System uses the inherited desktop display. OpenSSH compatibility supports System, and a saved TermCraft selection produces an explicit message when the SSH engine is switched to OpenSSH.

Requesting a TermCraft display from Local or embedded SSH starts the managed worker when necessary. Concurrent requests wait on the same startup. The worker publishes its display and authority path after the X01 authenticated readiness check. Startup failure or cancellation reaches the session tab, with a System option when the desktop has an existing display. Every launched Local process gets its own `DISPLAY` and `XAUTHORITY` values. X11 selections are shared between clients on the owned display. This change adds no clipboard bridge to the host desktop.

Embedded SSH binds to the selected display generation and makes one forwarding request on the authenticated terminal session. The protected cookie reader and constant-time setup verifier are reused for both display sources. The SSH protocol requires confirming channel transport before setup bytes can arrive. Each relay validates the bounded setup packet and its connection's random substitute cookie before opening the local X socket and replacing the cookie with the display's credential. The target handler admits at most 16 forwarding channels, after it requests X11. Gateway handlers and source-only connections have no forwarding responder.

Drop of the session forwarding lease expires those relays. Stop of the owned engine expires all bindings to that display generation and preserves the SSH shell and the pre-existing X server. Restart creates a fresh generation. Only the display source selection persists in the session profile. The sealed X01 launch, listener reservation and engine verification are unchanged.

- Full integration and formatting gates are collected with the parent execution batch. Native Windows/macOS engines, original-runtime comparison and desktop clipboard integration remain outside this evidence. The Linux fixture uses the real SSH/X11 protocols and packaged Xwayland with a headless compositor.

## Review follow-up

The embedded SSH worker now resolves its profile and configuration once, then requests a managed display from the workspace only when the effective options enable forwarding to the owned display. The worker uses the same resolved SSH options after it receives the display binding. The request is cancellable with its originating connection and starts before any SSH login. OpenSSH/System launch now reports an empty or unavailable `DISPLAY` before spawning the client when X11 is selected. Installed compatibility retains the existing explicit OpenSSH flags, including `ForwardX11=no` when the checkbox is clear.

- [Embedded RED](review-red-isolated.log) reproduced a trusted config enabling X11 after the workspace skipped startup. [OpenSSH RED](review-red.log) reproduced the process launch with an empty display.

Replacing the config while the display starts does not change the worker's resolved choice. A preferred config disabling forwarding opens the SSH shell without trying to start a deliberately unavailable bundle. With empty `DISPLAY`, explicit OpenSSH forwarding gives a display error, and a normal OpenSSH shell still opens with forwarding explicitly off even if its config requests it.
- [Isolated forwarding GREEN](review-green-isolated.log) reran all three real SSH and X11 checks.
- Fresh X11 SSH unit tests passed **5/5**.
