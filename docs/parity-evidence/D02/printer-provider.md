# D02 embedded Linux printer provider

In an embedded Linux RDP profile, choose **Add printer mapping**, enter one existing CUPS queue, and enter the exact legacy printer driver name installed on the remote Windows host. Choose a queue and driver that agree on the raw printer data format. This path needs the local system CUPS socket at `/run/cups/cups.sock` and a CUPS queue that accepts `application/vnd.cups-raw`. New sessions share no printer. Saved profiles store the queue and driver name. View-only profiles reject printer mappings. The installed Windows client's existing all-printers option remains separate.

The helper advertises one legacy printer on RDPDR with the selected names. It leaves the default-printer and XPS flags clear. Each job has an anonymous private file. Writes append in arrival order. A successful RDP close submits a complete IPP Print-Job for a nonempty document. A malformed or oversized write retires the affected job, and disconnect discards open jobs. Limits are 64 KiB per write, four open jobs and 32 MiB per job. The shared device worker bounds requests in flight. The CUPS upload and response have a ten-second deadline and observe channel cancellation. CUPS may already own a job by the time the RDP session disconnects or the reply times out. The helper never retries job submission automatically.

The Unix socket inode is opened before certificate negotiation and shared across connection attempts. Before each attempt, the helper checks local peer credentials and asks the pinned CUPS endpoint whether the selected queue accepts jobs in the raw format. A successful write-to-queue response needs a valid IPP job ID, URI and state. If CUPS cannot confirm the job, the session advises checking the queue before retrying. Only the fixed system socket and selected queue receive submissions. Remote file paths, printer cache names and driver blobs cannot redirect the local output or rewrite saved configuration. The provider never requests local print credentials.

## Verification

- The initial helper probe failed because the explicit printer mapping and channel were absent. A follow-up behavioral regression caught a truncated write leaving a partial job eligible for submission. The corrected test verifies an invalid-data completion, a retired handle and no connection to the IPP endpoint.
- The Linux helper fixtures deliver print bytes to an owned Unix IPP socket. They assert the actual connector attachment is absent for default settings, the printer capability and legacy queue and driver names are present when enabled, writes preserve byte order, IPP rejection returns RDP failure, malformed requests and spool limits retire jobs, disconnect cancels an incomplete upload, a stalled upload response times out, and a replaced socket path cannot affect a certificate retry.
- An isolated native CUPS 2.4.20 daemon accepted the helper's real Unix-socket IPP request on the owned `Office` raw queue. Its socket backend forwarded the exact 45-byte PostScript fixture to an owned loopback sink. The retained CUPS spool file and sink output each had SHA-256 `da84987873369534a02c2f86ba3130cd00dfa720b2b0cb813a1b99fe7bc562f3`. The temporary daemon listened on its own socket and used a temporary config, spool and cache. An earlier `file://` test reached CUPS and populated its spool but produced no backend file, so the verification used its real socket backend. No physical printer or system queue was used.
- After review fixes, the helper suite passed 39 tests, including twelve printer fixtures. A fresh locked offline helper build passed, followed by 11 passing `rdp_options` tests and 10 passing `rdp_session` tests. Formatting checks passed. Repeat the socket fixtures with `CARGO_BUILD_JOBS=2 cargo test --offline --manifest-path engines/rdp/Cargo.toml`. The root options suite covers defaults, round-trip persistence, input validation, Linux capability gating and the view-only and installed-adapter rejections.

The [printer review follow-up](printer-review.md) records the stale-handle, queue-readiness and IPP response fixes and their regression evidence. Smartcards and Easy Print/XPS remain open. The tests cover the legacy printer wire contract and the Linux CUPS submission path. They leave native Windows RDP driver negotiation, Windows/macOS local providers and physical printer output unverified. This increment leaves D02 open.

## Native provider source increment

The private native increment adds Windows Winspool and Darwin System CUPS providers for the same explicit legacy mapping. The native queue is retained in a bounded owned helper process, with no default lookup or discovery and no native call on the UI/RDP task. The [native design and evidence boundary](printer-native-design.md) records official source contracts, identity/cancellation rules and limits. Native component Rust typechecks and controlled Linux transports are evidence for source behavior only; Windows/macOS SDK linking, spooler runtime, remote driver negotiation and physical output remain unverified. This does not close D02 or add Easy Print/XPS.
