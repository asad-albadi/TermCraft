# D02 Windows serial mask-reset admission

This private candidate extends the existing bounded Unix mask-reset escape to Windows serial mappings. The integration payload is exactly three Rust files under `payload/` and the same change in `integration.patch`. The originals in `base/` were compared byte-for-byte against both unchanged MAIN and package source `c7fe0daa74512a18adbcdda680aa07d6ecf1d1cc82dd70f4f3a7994dbca8b31a`. No MAIN source, UI, README, hardware or host service was touched.

## Source trace and precise scope

- `src/desktop/options.rs:128` caps a session at 16 mapped serial ports. `devices.rs:41` bounds ordinary device requests at 16. `devices.rs:1058` decrements that count only when protocol-side polling retrieves a worker completion.
- `serial_windows.rs:415–469` verifies minor and live handle identity, then passes existing pending status for the same device into the Windows validator. `serial_windows_control.rs:81–90` permits exactly one WAIT_ON_MASK per device with read access. Native operations in `serial_windows.rs:293–333` keep an incomplete overlapped wait pending without a worker timeout. `devices.rs:969–1024` uses a 5 ms receive timeout only to interleave jobs and native readiness polls. Sixteen such waits can therefore occupy all ordinary credits indefinitely while their devices are idle. Before the patch, a valid Windows SET_WAIT_MASK was refused with DEVICE_BUSY before it reached the worker.
- `devices.rs:943–953,1173–1183` now applies the same serial device range and bounded reservation to Windows. There are still 16 ordinary credits, a threshold of 17 for mask reset, and a threshold of 18 for CLOSE when at least one serial mapping exists. A serial-free channel keeps both queues at 17 with only one CLOSE reserve. This maintains the existing Unix threshold design and does not add per-device credits.
- `serial_windows.rs:5` re-exports the Windows shape predicate. `serial_windows_control.rs:31–35` accepts the exact SET_WAIT_MASK code and uses the existing worker validator for input length, exact body size, maximum output capacity, and Windows-defined mask bits (zero or any 0x1fff subset). The channel separately requires major 14, minor zero, and a mapped serial ID. Drives, unmapped IDs, malformed bodies, unsupported mask bits and unknown controls cannot borrow the reset credit. Unix still uses its existing RXCHAR-only classifier.
- The admission predicate intentionally does not know live handles or their access. `serial_windows.rs:147–189,415–469` still denies disallowed CREATE access and requires the matching logical handle; `serial_windows.rs:240` still invokes the validator with the real rights before any native call. Neither worker scheduling nor native completion/cancellation semantics changed.

## Evidence and limits

- `red.log`: 10 passed, 2 expected failures, exit 101. Exact baseline Windows queue/credit selections refused the saturated valid non-RXCHAR reset and the saturated well-shaped reset destined for read-only access checking.
- `green.log`: 12 passed, 0 failed, exit 0. Three controlled admission cases cover 16 ordinary waits, the exact bounded reset shape and malformed variants, retry after reset alone, independent CLOSE availability after an admitted reset, both queue bounds, full credit reuse, no serial map, and read-only denial via the actual Windows validator. The other nine are unmodified Windows control tests. The helper extracts the real job/results queue sizing, credit gate/failure encoding and poll accounting. It selects Windows cfg and uses deterministic, injected completions, not Windows serial hardware or a Linux PTY substituted for Windows. The absolute paths to the precise inputs and generated hashes are reflected in `base-admission-inputs.json` and `source-admission-inputs.json`.
- `green-linux-helper.log`: 76 unit tests plus 10 integration tests passed, zero failures. This includes the existing native Linux PTY saturation/reset/CLOSE regression. The initial private-name build failed because the PC/SC fixture embeds the original executable name at compile time. The private candidate fixture was adjusted to find its private helper, then the full helper suite passed. Identity-only changes do not enter the payload.
- `green-windows-msvc.log`: Windows native source component plus tests typechecked for x86_64-pc-windows-msvc with installed Rust 1.99.0 stable target std. It compiles actual `serial_windows.rs`, the control validator/re-export, and native ABI checks. One unchanged unused drive-component variable warning. The existing native generator omits Channel, so `green-windows-admission-msvc.log` separately typechecks the exact Windows-selected admission fixture and its tests for the same target.
- `format.log`: scoped rustfmt check returned 0. `patch --dry-run -p1 -d base < integration.patch` accepted all three files. Local runs completed and no test fixture process was left running. No Windows native execution, hardware, RDP interoperation, full helper Windows link, or full app gate claimed.

## Follow-up observation, not changed here

`serial_windows.rs:123–138,172–189` pins one physical Arc<File> across logical close/reopen and certificate retries. GET_STATS is forwarded natively with the 24-byte Windows reply shape (`serial_windows_control.rs:67`, `serial_windows.rs:293–327`). Logical CREATE snapshots DCB and timeouts but captures no per-open stats baseline, so current source does not normalize physical-driver counters to a logical remote open. Whether and how native counters carry across logical opens needs separate Windows evidence. The patch neither clears device counters nor substitutes Unix counters. GET_COMMSTATUS is likewise untouched.
