# D02 serial controls and native device-source increment — 2026-11-25

This is a source increment for review, not D02 completion or native-device validation. The root coordinator owns checklist counts and the whole-application gate. No host serial device, printer, or smartcard was opened. Linux tests use owned pseudo-terminals, temporary files, and the existing private PC/SC fixture child.

## Changed source behavior

- Unix serial requests now support configurable read/write timeouts, accumulated reads and interval expiry, immediate and first-byte read modes, XON/XOFF characters, software pause/resume, break controls, DTR/RTS controls and modem queries. The POSIX handflow subset supports software flow and coupled RTS/CTS when the selected device supports its modem ioctls. Unsupported independent DSR/DCD/DTR handshaking, queue thresholds and character substitutions return explicit errors. PTYs reject modem queries and handflow instead of fabricating modem state; failed handflow probes leave termios unchanged. Mutating controls require a writable remote handle. Changed line/modem/flow/break state is restored or cleared on close, and queued operations retain their request-time timeout settings with timers starting when I/O can begin.
- The Windows serial provider uses an explicitly selected `\\.\COMn` endpoint, opened once with `CreateFileW(FILE_FLAG_OVERLAPPED)`. The opened handle survives certificate retries and remote close/reopen; unplug/reassignment does not reopen the visible COM name. `ReadFile`, `WriteFile`, `DeviceIoControl`, `CancelIoEx` and `GetOverlappedResult` operate on retained native buffers/events. Only explicitly implemented serial control codes and bounded input/output sizes are forwarded. Read-only authority, remote access checks, bounded queues and close cancellation remain enforced. Driver completion is awaited before native buffers are freed. A driver that never completes cancellation can retain its bounded worker/resources; the UI/protocol tasks never join that wait. Arbitrary device namespaces, automatic port discovery and event-wait controls remain unavailable.
- Windows regular-file allocation, rename and delete disposition use `SetFileInformationByHandle` on the opened source. Rename resolves one validated leaf relative to a capability-opened parent directory. The wire rename layout includes the one-byte reserved RootDirectory; disposition requires the protocol's empty buffer. DELETE access is requested only when authorized, and root read-only policy still refuses changes. Full 128-bit `FileIdInfo` plus the volume identity identifies opened objects, including ReFS-sized IDs. Open-file allocation queries use `FileStandardInfo` rather than estimating reserved space from logical EOF. Directory rename/delete and delete-on-close remain unsupported.
- Darwin allocation uses `F_PREALLOCATE`/`F_ALLOCATEALL`, requesting only the deficit from physical allocation and keeping logical EOF unchanged. `F_ALLOCATEPERSIST` is deliberately omitted so unused preallocation can retire on native close. Shrinking below EOF uses the opened file, consistent with existing allocation behavior. Native filesystem behavior remains unobserved.
- The embedded serial capability and device-path hint now include the Windows provider. Saved JSON fields/defaults are unchanged. Existing reviewed Linux CUPS/PCSC implementations are unchanged.

Linux/POSIX rename, disposition and delete-on-close still return unsupported. No path-check-then-unlink/rename is presented as an identity-safe operation. Windows destination resolution and native cancellation/allocation semantics require real endpoint validation before being counted as parity.

## Scoped review follow-up

The independent review recorded two Important Windows serial findings. Both are corrected in the refreshed candidate, pending independent rereview:

1. `ReadFile`, `WriteFile` and `DeviceIoControl` now receive null count pointers for overlapped dispatch. Counts are collected through synchronous `GetOverlappedResult` calls while their local count variables remain alive. The three arguments were inspected directly; no native runtime or memory-corruption claim is made. [ReadFile asynchronous contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-readfile)
2. Explicit close requests cancellation, waits for each Pending's terminal native outcome, then encodes that actual outcome. A write that completed normally retains its real successful byte count; successful reads/controls retain their real output; `ERROR_OPERATION_ABORTED` alone maps to cancellation through the native error mapper, and other native failures retain their mapped status. The boxed OVERLAPPED, buffers, event and handle stay alive until the wait returns. Drop retires outstanding operations without a response only when no protocol response can be delivered. The dedicated worker owns these waits, and no timeout permits early freeing of kernel-owned buffers. [CancelIoEx outcomes](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex), [GetOverlappedResult wait contract](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-getoverlappedresult)

`serial_completion.rs` provides the actual production completion encoder and cancel/wait sequencing seam. The existing forced-cancellation behavior was first extracted unchanged, with the terminal outcome deliberately discarded as in the reviewed close path. `d02-review-red-completion.log` records **three behavioral assertion failures**: successful write count, exact read/control output, and forwarding of non-abort failure. Correcting the seam to encode the terminal result made all three pass in `d02-review-green-completion.log`; the abort case also retains cancellation status. The native wait/cancel calls are injected at that boundary for these bounded, device-free tests; Windows API calls and timing were not executed on Linux.

`d02-review-green-serial.log` records the fresh scoped run: **16 serial/completion tests passed**, zero failed. `d02-review-windows-component.log` and `d02-review-macos-component.log` record fresh locked actual-source component checks with test source compiled, both passing. The Windows check retains the already documented unused metadata variable warning. `d02-review-format.log` is a passing changed-source formatting check. The earlier 44-unit/8-integration result predates these review fixes; this round did not rerun unrelated GUI/application or printer/PCSC suites. Component input proof now lists all production device modules and options, plus the generated Drives hash. Native close/cancel timing and hardware tests remain unrun.

## Remaining D02 work

Native Windows/macOS printer and smartcard providers are still absent. Serial wait/event masks, properties/status/statistics, queue sizing/purge and several less common control families are not implemented; unsupported calls remain explicit. Unix queue-threshold and independent modem handshakes are gaps. Windows regular-file native fixtures and Darwin allocation/close fixtures are compiled only. Full Windows helper linking/packaging, physical serial devices/modem/flow/unplug behavior, native RDP drive/admin/device/security/clipboard interoperability and comparison with original workflows remain unverified. Windows directory listing allocation sizes retain the older metadata-based estimate; native volume capacity queries remain unavailable. D02 stays open and no checklist count is advanced.
