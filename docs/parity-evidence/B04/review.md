## Findings

1. **P1 — Keep URL activation from supplying workspace options through Windows command-line quoting.** `target/agent-work/b04/review/new/src/platform/windows_integration.rs:77-83` interpolates `%1` into a quoted command argument; the protocol registration selects it at lines 109-113. Quotes inside the substituted URI can close that argument. For example, substituting `termcraft://session/id" --data-dir "C:\attacker` produces `"C:\Tools\TermCraft.exe" --open-url "termcraft://session/id" --data-dir "C:\attacker"`. The actual parser explicitly allows `--data-dir` alongside desktop launches (`target/agent-work/b04/source/src/cli.rs:106-121`), and `src/main.rs:32-45` selects that directory before the instance broker. The safe URL grammar sees only the already-separated `termcraft://session/id`, so its checks cannot reject the workspace override. This defeats the chosen-workspace inbound launch boundary once the new Windows protocol handler is registered. Add an activation-specific entry path which rejects all separately supplied workspace/action options and test the full registered command-line boundary, including quote-bearing payloads; preserve ordinary explicit CLI workspace selection separately. This is a source-derived command-line exposure, **not a claim that browser/native ShellExecute execution was tested**. Microsoft's [URI activation security guidance](https://learn.microsoft.com/en-us/windows/apps/develop/launch/handle-uri-activation) treats activation payloads as untrusted, and its [Shell verb guidance](https://learn.microsoft.com/en-us/windows/win32/shell/fa-verbs) identifies `%1` as Shell-expanded text.

2. **P2 — Connect removal to the package's owned handler lifetime.** The only package change is documentation (`target/agent-work/b04/review/shared.patch`, Windows README hunk). Actual `packaging/windows/install-per-user.ps1:149-160` moves/deletes the installed executable without removing its matching registry registrations or refusing while they remain. A user can opt in, then use the supplied uninstaller normally and retain Explorer/protocol/file commands pointing to a deleted executable. A subsequent version's ownership snapshot contains a different executable and refuses to take over those stale entries (`windows_integration.rs:125,169-170`), while the README-required exact old executable has gone. Make the uninstaller perform owned cleanup through the native implementation before deleting files, or explicitly refuse removal while matching registrations remain; test refusal/preservation for edited handlers and successful cleanup for owned handlers. The approved packaged-workflow contract requires preserving settings across install/upgrade/remove; a manual pre-uninstall README instruction alone leaves the supplied workflow incomplete. Coordinate any installer-helper edit with P08/root ownership.

3. **P2 — Make integration cancellation observable inside the operation.** `target/agent-work/b04/review/new/src/ui/windows_platform.rs:104` checks cancellation only before calling install/remove/status; `windows_integration.rs:149-197,251-311` never receives that token, and snapshot enumeration creates its own permanently-false token at line 274. Thus pressing Cancel during a lengthy preflight/snapshot continues all inspection and can subsequently create or delete registrations, even when cancellation occurred before the first mutation. The UI suppresses the final result at `windows_platform.rs:47-49` and reports cancellation, obscuring that work continued. Thread the request's token through status/preflight/snapshot and check it immediately before each mutation; stop future operations while retaining the documented limitation that an already-issued native write cannot be undone. Add a deterministic cancel-during-preflight fixture proving no later mutation starts. This is distinct from the acknowledged narrow native query/mutation race.

Existing values are never intentionally replaced, so no original-value restoration record is required for the currently supported absent-to-created transition.
